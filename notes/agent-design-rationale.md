# 内容任务规划 Agent 的构建思路

整体构建思路由笔者思考，与AI交流，以下内容有AI润色，但是核心的第一性思路以及五维度：可验证性、可回退性、环境确定性、自主性、合规性均有我指定，我与AI具体构建讨论思路、进行信息对齐

## 一、从任务目标出发

这个 Agent 帮助运营人员在给定预算和方案截止时间内，为虚构视频剪辑 App「帧剪」准备并保存一份内容活动方案。

运营提供主题、受众和创作要求，系统提供合成资料、工具费用与耗时表。Agent 需要查证产品和素材信息，形成业务简报，选择创作方向，编写脚本，组织制作安排，并根据检查结果修订。

最终交付包含两部分：

- **内容活动方案**：说明推广目标、受众、创作策略、内容安排、主视频脚本、素材用途和制作步骤，供运营审阅并继续制作。
- **执行报告**：说明任务计划、步骤状态、实际工具结果、费用和保存情况；任务未完成时，交代原因与缺口。

任务预算按合成费用表计量方案准备过程中的工具消耗，方案截止按模拟业务时钟判断。真实模型开销、后续制作和投放费用分别记录。

## 二、从第一性原理拆解任务

要完成这项任务，需要同时解决内容判断、实际执行和进度延续三个问题。

**内容创作需要理解和取舍。** 相同素材可以服务不同受众，用户要求也可能留下表达空间。模型适合结合目标、事实和反馈选择创作方式，业务 Skill 为这些判断提供方法。

**执行结果需要从环境中取得。** 模型生成的文字只能表达意图；费用是否发生、方案是否接收、文件是否保存，需要程序执行并返回实际结果。因此，模型通过工具行动，并根据结果决定下一步。

**多步任务需要独立保存状态。** 一次模型请求只能使用本次提供的上下文。任务跨越多个请求和进程，进度、成果、版本与消耗需要由系统持久保存，再把当前有效信息提供给模型。

由此形成基本运行关系：

```text
目标与约束 → 准备当前工作视图 → 模型选择动作 → 程序执行工具
                                  ↑              ↓
                                  └─ 观察实际结果 ─┘
                                         ↓
                           继续推进、请求澄清、完成或停止
```

模型负责理解、创作和调整，程序负责确定性规则与执行事实，用户负责关键取舍和最终采用。下面通过五个维度确定各部分的工程重心。

## 三、通过五个维度确定设计取舍

### 1. 可验证性：分开验证执行事实与内容质量

费用是否超限、引用能否定位、版本是否匹配、文件是否完整，可以低成本地由程序核对。主张是否得到原文支持、脚本是否满足要求、制作安排是否合理，则需要理解内容之间的关系。

因此，验证按判断对象分工：

- **程序验证规则和事实**：检查参数、引用定位、资源、版本关联及保存结果。
- **评估 Agent 核验内容**：在独立上下文中检查需求覆盖、事实支持、前后一致、制作可用性和不确定性，给出具体位置、依据及建议。
- **主 Agent 处理核验意见**：采纳需要修改的问题，或根据原始要求和材料作出有依据的驳回；必要时返修并重新核验。
- **运营决定是否采用**：结合实际业务需要，对方案作出最终判断。

核验和保存分别关联明确的产物版本。程序核实交付事实，模型提供内容判断，运营承担采用决定，各自的依据保持清楚。

### 2. 可回退性：稿件容易修订，消耗需要持续承担

当前 Agent 准备本地方案，没有真实对外发布动作。稿件可以形成新版本，旧稿可以保留，因此内容修订的可回退性较强。

同时，已经发生的费用和模拟耗时会随任务累计，恢复旧稿或重启进程都需要延续这些消耗。一次修改还可能带来重新核验和保存的成本，回退决策必须考虑完整剩余路径。

对应做法包括：

- 通过 Skill、工具说明和参数示例做好前馈，减少可避免的错误。
- 执行前检查资源和版本；涉及关键取舍时先向用户澄清。
- 估算创作、必要返修、核验和保存的完整费用与耗时。
- 保留成功成果及旧版本，返修时保护正确内容，复用适用结果。
- 中断后先核实已发生的动作，再决定如何继续。

可选改进根据收益与资源决定是否投入；必要修改缺少可行路径时，明确说明未完成原因。

### 3. 环境确定性：稳定规则交给程序，剩余变化通过反馈处理

合成资料、费用表和本地规则相对受控，模型输出、网络和进程运行仍有不确定性。提高确定性的着力点，是把稳定规则固化，并让每次实际变化都能被观察和追溯。

我们的做法是：

- **确定性工作由程序完成**：费用和耗时计算、结构校验、版本关联、状态记录及保存核实采用明确规则。
- **业务流程由 Skill 指导**：提供查证、创作、自检和返修方法，帮助模型保持行为一致。
- **执行依据随任务保存**：记录采用的资料、Skill、费用表和工具协议；更新通过显式采用留下变化记录。
- **异常产生可行动反馈**：参数错误说明原因和位置，重复错误追加提醒，失败和中断保留实际成果与消耗。
- **未知结果先核实**：尤其在保存已经产生副作用、回执尚未取得时，先确认实际状态。

这些做法让规则执行保持一致，让生成与运行中的不确定性有明确的处理路径。

### 4. 自主性：允许模型持续推进，同时设置明确的结束条件

完成方案需要跨多个步骤判断：资料是否充分、当前路径是否可行、意见如何处理、何时继续或结束。自主执行需要模型掌握当前目标、有效成果、剩余资源和待解决问题。

我们采用模型驱动的工具循环，由主 Agent 根据真实反馈选择动作。任务计划通过专用工具记录，在工作安排发生实质变化时更新，并关联已有成果和工具结果。

自主运行受到明确约束：

- 新任务默认最多 24 个主循环轮次，每轮一个动作，失败和非法响应也计入轮次。
- 关键缺口通过 `request_clarification` 交回用户决定。
- 无法满足条件时，通过 `stop_incomplete` 说明原因并保留成果。
- SQLite 保存输入、消息、版本、计划、核验和账本，续跑延续原任务进度与资源额度。

完成、待补充和未完成都有明确状态，使任务能够持续推进，也能够有依据地结束。

### 5. 合规性：明确授权、事实责任和追溯关系

当前任务使用合成资料、准备本地方案，外部操作风险较低。工程重点集中在任务授权、事实表述、信息保护和交付真实性。

对应设计包括：

- 模型使用限定的业务工具，Skill 和材料读取遵守任务范围。
- 材料正文按数据处理，用户目标和系统规则保持各自的授权来源。
- 创作中区分事实、建议、假设和未知；素材明确标注已有、待获取或待制作，并说明权利状态。
- 关键取舍由用户澄清，评估 Agent 只负责有限回读和核验，方案采用由运营决定。
- 输入、依据、产物、意见、处置和消耗保留关联记录，真实模型与 Mock 的身份和输出分别管理。
- 密钥保存在本地受忽略配置中，交付状态以实际记录及文件核实结果为准。

## 四、把这些判断组织成协作方式

### 1. 用一条主线保持创作上下文

目标、受众、表达方向、脚本、素材和制作安排彼此影响。让主 Agent 连续负责这些工作，能够保持判断依据和修改关系，也减少交接时重新组织上下文的开销。

主 Agent 直接创作并提交完整脚本，再引用脚本版本组织活动方案。创作知识通过 Skill 提供，内容核验使用独立且有界的评估上下文，职责清楚的同时保留完整创作主线。

### 2. 按用途与使用频率组织信息

模型需要在每一轮获得足够的信息，才能作出正确选择。我们把输入分为几类：

| 信息 | 承担的作用 |
| --- | --- |
| 系统提示 | 持续适用的职责、行动纪律、资源口径和完成条件 |
| 工具定义 | 能力用途、参数、执行前提和返回含义 |
| 业务 Skill | 创作与核验的方法、判断标准和条件性示例 |
| 当前工作视图 | 有效要求、成果、版本、资源和待解决事项 |
| 工具反馈 | 本次实际结果、错误、缺口和后续判断依据 |

任务类型已知时，预装必需方法可以减少读取回合。因此，主 Agent 默认预装创作 Skill，评估 Agent 预装核验 Skill，条件性参考通过 `read_skill` 按需读取。

系统规则和工具定义形成稳定前缀，新的反馈、状态和采用记录向历史追加。这样的组织便于复用稳定内容，同时保留变化的来龙去脉。

### 3. 围绕完整业务行为提供工具

工具的 interface 需要让模型知道何时使用、如何构造参数、调用会产生什么结果，以及失败后可以依据什么调整。名称、说明、输入、前置条件和反馈共同组成调用契约。

在创作提交上，`submit_script` 接收主 Agent 写好的完整脚本，校验后返回版本引用；`submit_campaign` 引用该脚本并提交其余活动方案，程序组装固定快照。成果通过结构化调用进入系统，再由程序导出为运营可阅读的内容。

费用、版本、核验和保存规则集中在程序中，让各个入口沿用同一套依据。模型据此选择行动，执行结果再进入下一轮上下文。

### 4. 让反馈支持下一次行动

一次工具调用之后，模型需要知道动作是否完成、产生了什么、条件发生了哪些变化。

因此，工具反馈保留实际结果、版本引用、必要消耗和具体缺口。参数错误指出位置，业务拒绝交代原因，中断记录未决状态。主 Agent 根据这些信息修正参数、调整方案、复用成果、询问用户或停止。

内容核验也采用同样的思路：意见给出具体问题和依据，主 Agent 明确记录处理决定，让下一次返修有清楚的修改目标。

## 五、用完整任务结果衡量设计

### 1. 从完整路径控制效率

一次调用的价格或速度，只能解释任务开销的一部分。我们更关注完成整项任务需要多少请求、返修、耗时和资源，以及最后形成了什么成果。

因此，流程按实际缺口展开：资料充分时直接创作，确有取舍时比较方向；首次脚本可以同时携带简报；任务计划在实质变化时更新；返修明确修改位置和应保留内容，脚本发生变化时提交完整新稿，其余适用成果继续复用。

可选建议根据具体收益决定是否采纳。资源估算覆盖当前已知的完整剩余路径，帮助模型在内容收益、返工风险和剩余额度之间作出选择。

### 2. 检查最终行为、状态与呈现

验证围绕公开 CLI、持久状态和导出结果展开，检查任务是否完成或正确停止、费用是否一致、成果是否保留、保存是否真实，以及方案是否回应要求。

测试同时覆盖正常与异常、应继续与应停止、应澄清与可直接推进等情境，并关注返修、输入变化、中断和复杂历史中的组合行为。真实缺陷的正确处理与误报的合理驳回，也需要分别观察。

确定性测试验证规则和流程，真实运行观察模型在反馈下的动作与内容表现，运营审阅关注方案能否用于后续工作。完整方案、执行报告和 Trace 分别服务成果阅读、过程核对和问题追溯。

## 六、整体构建思路

这套 Agent 围绕一项可持续推进的内容任务组织：模型掌握目标和上下文，Skill 提供业务方法，工具承接实际行动，程序落实规则与执行事实，持久状态延续进度，核验反馈推动修正，用户承担关键取舍与最终采用。

设计重心落在信息是否充分、职责是否清楚、反馈是否可用、资源是否受控，以及交付是否可信。各部分共同服务于同一个目标：在明确约束内，完成一份有依据、可审阅、可继续制作的内容活动方案。
