## 设计原则

状态：用户认可并要求持久化的本轮启发，用于后续改造和评审。具体提示词正文及工具字段仍是草案，未等同于逐字确认。

推导顺序继续采用 **目标与完成证据 → 信息和状态缺口 → 行动与观察 → 反馈修正 → 验证与终止**。DSH及commerce实践提供信息组织和工程取舍的参考，实际收益以本项目完整任务结果判断。

1. **整体设计每轮输入。** 主系统正文、原生工具定义、Skill、任务状态及真实反馈共同影响模型判断。按信息用途、使用频率和必要性安排位置；创作知识可预测时预装，条件性细节按需读取。常驻正文的长度由持续需要决定。沿用稳定前缀、工具顺序及变化追加原则，具体装载和版本见D-01、D-02、D-08。
2. **工具是面向模型的interface。** 名称、用途描述、输入字段、执行前提和返回含义共同决定工具是否易于正确使用。模型需要能据此选择能力、构造调用和理解结果；仓库里存在函数代码不等于模型已经知道怎样用。脚本版本提交与剩余动作估算按D-03、D-07落实，提示词、Skill和工具定义表达同一职责。
3. **反馈必须支持后续行动。** 工具返回应说明实际结果、缺口、版本及必要消耗；错误交代具体原因、动作是否启动或产生副作用，以及有依据的处理方向。保留事实、建议和未知的区别，让主Agent据此返修、复用或停止。具体输入及返回组织见D-08所链草案。
4. **语义判断与执行事实各有归属。** 主Agent承担表达、内容取舍、计划和评审处置；程序核对资源、版本关联、实际执行及保存事实。有界核验提供可处理意见及依据，模型判断仍需正反样例验证。各职责沿D-03至D-07执行，历史计划、旧评审和未知保存结果不得冒充当前成功。
5. **按具体缺口控制工程规模。** 借鉴DSH的信息所有权和调用链路，以本项目Python原生循环、工具定义及SQLite承载已确认责任。每增加一种机制，说明它解决的任务缺口或已观察问题及其成本；插件平台、额外Agent和复杂编排按真实需要另行论证。
6. **以完整任务结果判断改进。** 关注内容质量、事实支持、返修、实际开销、恢复与保存可信度；文本长度、工具数量或调用数仅作为过程观察。具体对照及保留失败的验收约定见D-06，运营使用价值与真实投放效果沿原有证据边界分别说明。

这些原则支持简单任务在已有依据充分时直接创作、提交版本、组织方案、核验和保存；额外查询、比较和澄清由实际缺口触发。该示例解释选择依据，不规定新的固定动作序列。

## D-01：Skill 载体与工具加载

状态：标准Skill机制、允许预装、Q14的受限读取范围及Q22的统一读取入口已确认，精确参数与实现细节待细化。

业务 Skill 采用每技能一个目录、以带 YAML `name` 和 `description` 的 `SKILL.md` 为入口的组织方式。description 提供首次选择所需的能力与适用条件；正文提供方法；仅特定分支需要的细节由带触发条件的指针引向引用文件。`scripts/`、`references/`、`assets/` 按实际用途添加。

产品业务 Skill 随实现仓库交付，本项目采用 `content-task-agent/.agents/skills/<name>/SKILL.md` 的常见项目级组织，由产品自身加载。父项目供开发 Agent 使用的技能与产品业务技能分别管理；更广的用户级扫描、多来源优先级和热更新尚未纳入改造范围。

模型主动激活的目标链路：

```text
程序发现元数据并提供目录与调用指引
→ 主 Agent 结合当前任务、状态和 description 判断适用
→ 主 Agent 发起工具调用
→ 程序校验并读取正文，返回内容与资源基址
→ 正文作为工具结果进入连续历史
→ 主 Agent 运用方法，遇到引用分支时再调用读取工具
```

Q14确认采用面向Skill的受限读取能力：模型按Skill名称取得正文，再读取其引用资源；程序负责解析资源位置和任务采用的版本。本轮提供完成这项工作的interface，不开放任意仓库文件访问。Q22进一步确认正文与引用共用一个读取入口，以read_skill作为讨论名称：提供Skill名称时读取正文，增加相对资源位置时读取引用；范围、来源和采用版本统一处理，精确字段待细化。加载 Skill 为当前 Agent 增加方法，不自动新增 Agent，也不自动执行正文提到的脚本或读取全部引用资源。首次适用判断依赖模型可见的 description 和调用指引，正文内的“何时使用”不能独自承担首次发现。

加载通路与装载时机分别设计。任务类型或调用目的已能确定必需知识时，可以保留程序预装，避免额外回合；条件性方法和资源经指针及工具按需读取。固定预装本身不是已证实缺陷，标准载体和工具读取链路的差距仍需补齐，具体取舍见[本轮分析](design-analysis-2026-10-29.md)。

用户已确认机制必须按主流Skill做法落实：名称和描述用于发现与选择，正文经工具激活或明确预装进入上下文，引用资源继续按需读取；预装和工具加载读取同一份标准Skill并沿用相同的内容组织、来源与版本记录。预装以真实宿主上下文记录，不伪造模型工具调用。具体工具名称不构成规范要求；仅改文件名或继续维护另一套独立知识注入文件，不构成机制完成。

## D-02：与现有上下文管理衔接

状态：保留既有原则，补齐 Skill 装载后的生命周期。

继续参考 DSH 的目录摘要、正文工具结果、连续历史及变化追加做法，保持本项目原生循环和可核实续跑。已加载且仍有效的内容沿历史复用；任务恢复继续使用实际加载的正文与版本，采用新版时记录变化和结论适用性。本期沿用不做上下文压缩的既有范围。

DSH 的目录去重不等于正文硬去重；再次正常加载会读取当前文件。借鉴其加载通路时保留本项目的任务冻结和显式采用行为。历史追加有利于前缀复用，实际缓存收益仍以请求用量记录判断。

Q15确认默认装载策略：主Agent初始化时预装创作Skill正文，独立核验初始化时预装核验Skill正文；各自明确记录来源、版本和已加载状态。条件性引用资料继续按需读取，以后新增其他Skill再根据其适用条件选择。主循环已加载不代表核验调用已经获得，创作职责按D-03确认由主Agent完整承担。

尚待细化：目录与正文怎样表达已加载状态；引用读取权限和资源基址如何衔接。Skill读取不另设模拟生成费，真实发生的模型请求、用量和所占回合按实际记录；预装不伪造请求。

Q21确认本轮暂不新增独立的产物回读工具。按当前不压缩、恢复完整合法历史的约定，创作提交正文保留在实际调用历史中，人工稿导入及必要的宿主内容注入提供相应正文；版本回执和状态变化说明适用性。材料与Skill引用继续使用各自的读取能力。后续出现具体的信息缺口或定位困难时，再据此决定产物回读interface。此取舍不扩大为删除历史正文或对内容不可见仍声称已读。

## D-03：主 Agent 承担完整创作

状态：用户已确认职责归属，代码改造尚未实施。

主Agent在连续任务上下文中运用创作Skill，负责简报、策略、活动安排、主脚本、素材用途、制作步骤及返修的完整创作。后续改造取消当前必须交给独立脚本生成模型调用、再整合回主循环的交接；主Agent直接承担脚本创作与修改。

Skill提供方法，工具承接资料读取、估算、产物提交和保存等实际操作，主Agent运用方法并决策。用户已确认脚本生成能力通过“主Agent在结构化工具调用中产出脚本 → 程序接收、校验、保存版本并返回反馈”表达，工具内部不再另启创作模型；文档如实说明模型生成与工具处理的职责。生成模式按D-05取消固定三候选，模拟计量按D-07绑定正式脚本提交/返修尝试，具体价目表及interface由实现落实。原有独立核验安排及硬约束继续有效。

用户进一步确认：脚本提交后获得明确ID和版本，完整方案提交引用该脚本版本，由程序组装包含全部内容的方案快照，避免主模型重复输出同一脚本。脚本修改形成新版本，不自动改写旧方案；核验针对当前完整方案，覆盖脚本、素材及活动安排的关系。输入、产物和核验的版本适用性继续核对。

Q16确认脚本返修提交完整的新脚本，并关联修订所依据的旧版本。本轮不引入修改补丁的提交方式；局部返修表示创作判断和修改范围可以局部化，提交结果仍形成完整、独立可读的新版本。短视频脚本规模有限，此取舍优先保持提交和恢复契约简单；完整活动方案继续引用脚本版本，不再次重复输出脚本。具体提交字段待细化。

Q24确认业务简报保留为可回查依据，独立提交为可选入口。需要先沉淀目标、事实或未知时可以单独提交；依据充分时允许随首次脚本提交一并保存；已有适用简报直接引用。此确认取消每次必须单独提交简报的要求，精确字段仍待细化。

Q26确认联合提交整项接收：执行前整体校验，全部有效才启动业务尝试，成功时一并保存简报和脚本版本。校验失败不形成其中任一新产物版本，实际调用和具体错误仍保留；启动后的失败、中断、消耗与未知结果继续按既有规则如实记录和恢复。本轮不增加“校验拒绝但另存有效部分”的接收分支。

该决定来自本轮用户明确确认；旧三方式对照没有单独隔离生成分工变量，仍不将历史证据表述为已证明合并的质量或成本收益。后续通过改造后的行为及完整开销验证设计效果。

## D-04：按完成条件重审过程与上下文职责

状态：用户已确认过程按需选择、开放创作方向、本轮保留单动作执行及Q17的专用计划更新能力；既有硬约束继续有效。

主Agent依据任务需要选择比较策略、记录选择、直接创作或局部返修，不再将“比较 → 登记 → 创作”设为每次必经顺序。程序继续落实产物完整、依据、资源、有效核验和核实保存等完成条件；强制中间步骤须有防止具体失败的依据。

功能演示、用户情境、教程作为创作Skill的参考方法，不再作为排斥其他合理方向的硬枚举。允许主Agent提出混合或其他方向，并说明目标、材料及完整路径可行性；程序按实际工具动作核算消耗。主提示、Skill及核验提示的指导继续按频率和职责确定权威位置，具体interface在已确认职责内细化。[依据与取舍](design-analysis-2026-10-29.md)

Q25确认旧compare_strategies与choose_strategy两个独立入口退出新任务工具集合。主Agent运用Skill按需比较表达方向，在完整方案中记录选择及理由；数值估算交给成本工具，保留比较与追溯责任。此决定不扩大为每次必须新增比较或登记回合，也不删除旧任务固定代码和历史证据。

用户已确认任务计划由主Agent按实际任务提出和更新，替代仅以固定四阶段投影作为整份任务计划的做法。计划关联实际成果及工具反馈；程序核对执行事实，核验和保存状态必须来自真实记录。

Q17确认提供专门的计划更新工具，在建立计划或计划实质变化时持久记录。业务工具继续返回执行事实，计划步骤关联实际成果和反馈；不要求每次动作前后额外更新计划，也不要求各业务工具参数重复携带计划更新。具体工具名称、计划结构及关联字段待细化，计划不能充当执行成功或业务合格的证据。

本轮保留一轮一个工具动作，先通过取消强制中间步骤、独立生成交接和重复输出降低开销。多工具协议能力与宿主并发执行分别看待；并发留待出现真实瓶颈后再论证，不作为本轮改造项。

## D-05：内容选择与评审处置的有效性

状态：有据驳回、取消固定多候选模式及Q20的原始要求引用方式已确认；具体字段待细化，未复现新的质量事故。

用户已确认取消固定“直接生成/生成三个候选”模式及按分镜段数选优。主Agent在确有取舍需要时提出候选，围绕目标比较开场、表达或节奏；简单任务可直接创作。是否继续投入取决于具体收益、反馈及剩余资源，实际创作和返修尝试的计量继续细化。

用户已确认驳回必须明确关联原始要求或材料片段，并对应当前稿件和意见版本；程序核对引用与版本，主Agent判断依据在语义上是否支持驳回，不能仅凭非空自由理由解除阻塞。用真实缺陷被错误驳回、误报被有据驳回的正反样例验证；暂不规定每次驳回都新增一轮评审。具体证据字段及候选质量比较interface待细化。[具体代码与验证问题](design-analysis-2026-10-29.md)

Q20确认原始要求引用采用“输入版本＋字段位置＋原文片段”，例如输入v3中requirements[1]的相关原文；本轮不为每条要求增加长期稳定的独立ID。材料依据继续引用材料版本及相关片段。程序核对定位、原文与版本，主Agent判断语义支持关系。字段位置在所引用的输入版本内解释，避免把新版列表的位置套回旧版；具体字段命名和编码仍待细化。领域含义见父项目[GLOSSARY.md的原始要求引用](../../GLOSSARY.md)。

Q23确认单条与多条评审处置共用一个支持列表的入口，以record_dispositions作为讨论名称。单条采用单元素列表，多条集中提交，每项分别关联意见、决定、理由和必要依据。

Q27确认整批先校验，全部有效才记录处置。有无效项时返回具体位置及原因，原处置状态保持，主Agent按反馈修正后重新提交。本轮不采用有效项已记录、无效项被拒绝的部分接收方式。此约定描述接收语义，不能替代对运行中实际故障、副作用及未知状态的如实记录。

## D-06：设计效果与运营使用证据

状态：Q12确认本轮对照验收方式；运营使用反馈仍属后续建议，真实投放、跨任务自动学习及协作平台继续在原范围之外。

本轮使用同一批业务场景与内容评价标准对照新旧版本，补充Skill按需读取、直接创作、局部返修、脚本版本引用及有据驳回等新机制场景。预算、版本、恢复和保存等硬要求继续通过；内容评价尽量隐藏新旧版本标签，全部结果及失败保留；比较完整任务内容质量、请求数、耗时和返修情况。旧测试按新interface调整，保留有效需求断言，不以测试数量或每个场景调用都下降为目标。

带历史负担、相邻能力组合的成对场景继续作为具体评估设计依据。旧三方式对照未隔离证明每项设计收益；可从当前人工稿协作入口收集运营使用缺口，但尚无人工修改成本的实测结果。[评估范围](design-analysis-2026-10-29.md)

## D-07：新创作提交的计量与版本一致性

状态：Q8至Q10的计量、估算及新旧协议处理，以及Q19的首轮能力概览已获用户确认；以下当前实现差距由静态阅读确认，未做故障复现。

用户已确认模拟生成费绑定一次正式脚本提交或返修业务尝试。Skill读取、计划整理和复用已有脚本组装方案不另收生成费。执行前拒绝不收费，已启动后的失败或中断保留该次费用与模拟耗时，同一次尝试恢复或结果复用不重复计量。真实API请求和可得用量逐次另记，继续与模拟工具费及活动制作投放费分开。

主Agent提出完整剩余动作清单，成本工具按适用费用表计算，不再按创作方向标签套固定路径。程序核对已知必需的核验、保存已纳入估算；实际反馈改变条件后重新估算。清单表达当前计划，不锁定后续动作顺序。

Q19确认首轮提供小规模适用动作概览，包含费用、模拟耗时、单位、失败计量规则及费用表版本。具体剩余路径仍交成本工具核算，实际消耗由执行反馈提供；能力概览、估算和执行共用同一适用费用表，后续追加变化和消耗状态。此确认规定输入内容和来源，具体展示格式仍待细化。

当前任务记录了pricing_version，但运行、核验和保存的费用表加载没有按任务记录的版本选择，而是读取当前环境/default；历史账本保留原来源，未来执行存在价格依据漂移的可能。[费用表加载](../src/cta/pricing.py)、[运行](../src/cta/loop.py)、[核验](../src/cta/review.py)、[保存](../src/cta/save.py)。后续按已有版本一致性原则集中落实估算与执行使用同一适用表，不将记录版本字段等同于执行版本已锁定。

现有主消息和工具schema可冻结，但handler仍来自当前代码，尚无按旧协议选择旧业务实现的机制。用户已确认新任务采用新设计，旧任务保留原数据并通过固定旧代码恢复和复现；本轮不建设自动迁移或双协议执行层。后续保留明确旧版本入口，新代码遇到旧协议需如实说明适用版本，不能将保留历史记录解释成自动兼容。

## D-08：主系统提示词与内容分工

状态：用户询问后形成草案，Q18已确认业务对象版本选择职责；具体正文、字段尚未整体确认或接入运行代码。

[主系统提示词草案](main-system-prompt-draft.md)保存常驻正文及其与Skill、工具定义和动态消息的分工。正文围绕完整创作责任、信息缺口、工具反馈、事实与资源口径、版本和完成条件组织；具体创作方法、样例及参数结构放入其所属Skill或工具。草案只作静态情景核对，实际效果待接入后的对照验收。

[模型输入与工具调用草案](model-input-draft.md)进一步记录原生tools字段、任务能力与费用消息、assistant/tool往返及协议差异，补齐仅讨论常驻正文的不足。新工具定义必须与新职责一起调整，不能保留旧固定策略和独立生成参数后只重写system正文。

Q18确认模型明确选择要处理的业务对象版本：完整方案引用脚本版本，核验和保存引用方案版本，意见处置引用对应评审和意见。程序检查引用及结论适用性；任务归属、调用ID、费用表版本和新版本编号由宿主管理。引用的是宿主已提供的实际对象，不要求模型自行编造版本或复述宿主配置。具体引用结构待细化，当前代码中部分工具自动取当前对象的行为仍待改造。

DSH实际persona及工具sections的补读依据见[研究记录](../../.scratch/content-task-agent/research/dsh-system-prompt-reading-2026-10-29.md)。草案区分工具用法指导、原生工具定义、运行时能力信息与实际返回；保持本项目Chat协议，不直接复制DSH的Messages序列化或插件体系。

## 后续验证应回答的问题

- 任务适用但没有点名 Skill 时，模型能否从描述选择并实际读取；任务不适用时是否误触发。
- 正文中的条件指针能否在对应分支引导引用读取，其余分支是否避免无关加载。
- 加载失败能否产生真实可行动反馈；加载成功的正文是否进入后续模型输入并实际被使用。
- 已加载内容与跨进程续跑是否保留正确版本，显式采用新版是否保留变化记录和结论适用性。
- 与原有输入、预算、截止、轮数和保存规则组合后，质量和完整开销如何变化。

这些是后续验证方向，具体样例随方案细化。文件格式校验不能代替上述行为证据；本轮没有执行新测试或业务模型调用。
