# 工单 11：真实主模型处置与返修成对探针

## 方法与局限

- 代码基线 `16a1716`，其后只同步进度提交 `dfd6ac7`；主模型和后续复核均为 DeepSeek `deepseek-flash`、SDK 直连、非思考、非流式、零 SDK 重试、默认 TLS。真实 `.env` 仅在调用时加载，原值不进命令行、日志或仓库。
- 两个样例的前置简报、脚本、方案及首条核验意见通过公开 CLI 和现有 `ScriptedClient` 接入，全部为**合成 Mock 前置**，不是模型生成或真实核验。两稿唯一变化是第 1 段口播：真实缺陷稿为「使用帧剪保证涨粉」，误报稿为「让片段对齐节拍」。两者收到相同的脚本化必修意见，指出该处承诺涨粉、违反 M-004。标签及来源见 `fixtures/eval/redesign-semantics-main-v1.json`。
- 分别把前置任务数据库以 SQLite backup 复制到各自独立的 `real` 数据目录后，使用公开 CLI `resume` 逐轮执行真实主模型及其调用的真实复核；原 `mock` 目录保持不变。历史请求仍标 `mock=1`，后续真实请求标 `mock=0`，初始核验不能当成真实模型结果。复制任务的持久 `mode` 仍为 `mock`，恢复快照中也会显示该值：这是混合前置实验的显著污染，不能视为从头到尾纯真实生产任务，也不能排除其对模型的影响。
- 每次 `resume` 使用单轮调用上限，以在每轮落盘和检查；并非增加任务原有 24 轮上限。每轮都会附加恢复事实和状态快照，因此本实验的上下文与一口气运行的真实任务不同。模拟预算、截止时间、任务上限及保存条件仍由产品执行。样本只含一对，不推断泛化率。

## 真实缺陷：采纳、版本引用与返修

- 初稿脚本 `o_81885402898687fc` v1 的 `segments[0].voiceover` 明确承诺涨粉；M-004 明确禁止。主模型对模拟意见 F1 作 `accepted`，理由指出原文和 M-004，**没有错误驳回该缺陷**。因此本例观察到的是正确采纳，不是一次实际发生的错误驳回。
- 新脚本 `o_7736f2a3988e7188` v2 引用 v1 为 `revises_script_ref`，完整提交新脚本；方案 `o_a5fccdb2f10021c2` v2 引用脚本 v2。新稿删除涨粉口播，但从 15 秒、单段改为 30 秒、三段，明显扩大改写范围；用户未要求更改时长，不能仅凭通过引用检查就宣称保留了所有无需修改的内容。
- 后续**真实独立核验** v2 判 `fail`，指出未授权 M-006《Late Bus》使用表述、未有材料支持的 UI 顺序等问题；这些是第一次返修引入或暴露的回归风险，不应略去。模型处置后提交脚本 `o_959242936fa62958` v3，引用 v2，并提交引用脚本 v3 的方案 `o_d118ac4f9bf7f384` v3。真实复核 v3 为 `pass`（仍有两条可选建议），最后核实保存成功。
- 人工复核：最终稿对《Late Bus》标为待授权且有未授权不发布门禁，但默认替代曲目只写「已授权曲库曲目」，未列出具体可用曲目及其权属证明，制作前仍需落实；录制步骤还有「角目」笔误。模型复核通过不代表所有制作细节或无关内容保护均已完美。

## 误报：驳回依据和失败

- 当前脚本唯一口播为「让片段对齐节拍」，未出现核验意见所称的涨粉承诺。主模型第一次驳回时引用 M-001 的真实正文，但将 scope 写成「iOS/Android 4.2 及以上；15/30/60 秒成片」，并非材料范围原文连续片段；`record_dispositions` 返回 `invalid_evidence`，整项未接收。该失败完整保留。
- 模型随后修正为 M-001 的完整原文范围并再次提交，同一 review ID、方案 v1 和 F1 的驳回被接收。其理由准确指出脚本实际口播与意见不符；M-001 引文支持「片段对齐节拍」，但单独的材料引文本身并不能证明脚本不存在涨粉承诺，必须结合被审脚本原文判断。程序同样明确提示“依据可定位不代表语义支持已验证”。
- 该样例保留脚本及方案 v1，未重新核验，保存记录显示已核实。它证明这一次误报被有据处置，不证明其他误报均可正确识别。
